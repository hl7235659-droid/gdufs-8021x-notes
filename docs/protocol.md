# 协议：有线 802.1X + 锐捷私有段

> 证据口径：本文所有"观察到"的内容都来自本地离线解析；不含账号、MAC、口令派生值。
> 签署与哈希相关的部分见 `signature.md`。

## 1. 一次完整认证（两轮 MD5）

```
[客户端] EAPOL-Start                      (锐捷组播 01:d0:f8:00:00:03；18 字节裸帧)
   ←   EAP-Request/Identity
[客户端] EAP-Response/Identity            (EAP 长度字段 16；载荷只有用户名，不含私有段)
   ←   EAP-Request/MD5  (challenge = 16 字节)
[客户端] EAP-Response/MD5                 (EAP 长度 412 / 私有段 390，见 §3)
   ←   EAP-Request/MD5  (第二轮请求：正常时为 ~200 字节计费/服务段；拒绝时为 0x66+0x53+0x66)
[客户端] EAP-Response/MD5                 (与第一轮同构，仅摘要与挑战派生字段不同)
   ←   EAP-Success   或   EAP-Failure
   ←   之后每 ~30 s：EAP-Request/Identity → 客户端回 Response/Identity（保活）
```

要点：

- **两轮**：服务器会下发两次 MD5 挑战（值相同），第二轮用于携带服务/计费结果。
- **固定属性集**：两轮 Response/MD5 的属性集、顺序、长度完全一致，**只有摘要与挑战派生字段（`0x2f`/`0x4d`/`0x60`）不同**。
- 第二轮请求里若出现 `0x53` 属性，说明服务器给出了**判决文本**（见 §6），此时最终帧为 EAP-Failure。

## 2. 私有段的两种格式

### 2.1 裸格式（本校区服务器→客户端使用）

```
<type:1><len:1><content:len>  串接
```
- `len` 是 content 的字节数；无 magic、无外层封装、无结尾头。
- 本校区第二轮那个 ~200 字节的服务段，就恰好由 17 个这样的 TLV 走完。

### 2.2 封装格式（客户端→服务器使用，历史实现里叫 "magic"）

```
<0x1a><总长:1><00 00><13 11><type:1><len:1+2><content:len>...
```
- 与官方客户端观察值逐字节一致；`len` 字段比裸格式多 2。
- EAPOL-Start 也可以携带一整个封装私有段（官方客户端在某些时刻发 ~518/576 字节的 Start）。

### 2.3 两条必须记住的规则（历史缺陷的根因）

1. **追加私有段之后，必须同步两个长度字段**（EAPOL 的 length 与 EAP 的 length，均为大端）。
   否则服务器按长度只读到帧头，**整个私有段会被当作填充丢弃**——这是历史上失败最多的一条。
2. **私有段只加在 MD5 应答上**。加在 Response/Identity 上会被服务器拒绝（Identity 应答只允许纯用户名）。

## 3. 属性表（客户端 → 服务器，EAP-Response/MD5）

以下为"裸格式、无 IPv6 属性"时的 15 条（长度单位为字节）：

| type | len | 含义 / 状态 |
| --- | --- | --- |
| `0x11` | 36 | 客户端标识：`"8021x.exe"` + 补零 + 版本字节（本版本为 6.86）。长度字段是 36，不是字符 `'$'` |
| `0x50` | 17 | DHCP/地址信息：掩码 + 网关 + DNS + 固定尾字节 `0x01`；**自身 IP 恒为 0（不上报）** |
| `0x76` | 0 | 观察到恒空 |
| `0x2d` | 6 | 本机 MAC（**本笔记不展示**） |
| `0x63` | 1 | 观察到常量 `0x01` |
| `0x2f` | 16 | **口令派生值**（随挑战与账号口令变化）——本笔记只记录"存在此属性"，不提供任何取值 |
| `0x4d` | 128 | 客户端签名（ASCII hex）——见 `signature.md` |
| `0x60` | 128 | 与 `0x4d` 逐字节相同 |
| `0x54` | 15 | 序列号，形如 `Static:<serial>`（未确认服务器是否校验） |
| `0x62` | 1 | 观察到常量 `0x01` |
| `0x6b` | 1 | 观察到常量 `0x00` |
| `0x70` | 1 | 观察到常量 `0x40` |
| `0x7e` | 8 | 观察到常量（形如 `00 00 01 00 00 0c 00 00`） |
| `0x6f` | 1 | 观察到常量 `0x00` |
| `0x79` | 1 | 观察到常量 `0x02` |

官方客户端在同一接入点上还会**额外**发出 4 条（插在 `0x63` 之后）：

| type | len | 含义 / 状态 |
| --- | --- | --- |
| `0x35` | 1 | IPv6 计数（观察到 `0x03`） |
| `0x38` | 16 | IPv6 相关属性（语义未确认） |
| `0x36` | 16 | link-local 地址形态（语义未确认） |
| `0x39` | 32 | 服务名（官方在 md5 轮里给出，如 `after-auth` + 补零） |

> **注意**：本地可用的第三方实现即使缺这 4 条也曾通过认证；因此它们**不是通过认证的必要条件**（至少在本接入点如此）。是否必要因楼栋/设备而异。

## 4. 保活

- **服务器每 ~30 s 发 EAP-Request/Identity，客户端回 Response/Identity 即可**（载荷 11 字节用户名）。
- 观察到的 15 分钟会话里**没有任何专有 keepalive 帧**；不要开启锐捷专有 echo（历史实现的 `heartbeat` 设为 0 更贴近实际，并需在 Success 后应答 Identity 轮询）。
- 若客户端在 Success 后仍把状态机复位，会丢掉会话信息、无法应答轮询——这是需要修的一处（见 `implement.md`）。

## 5. "二次认证"与 DHCP

- 私有段里 `0x50` 承载地址信息，`dhcp-type` 之类的参数决定是否在认证后触发一次 DHCP 事务。
- 本接入点观察到：服务器不要求额外的专有二次认证流程；第二轮 MD5 即是"二次"。
- **重要现场事实**：交换机侧按 **DHCP 事务**维护 IP↔MAC 绑定（DHCP snooping + DAI/IPSG）。
  用**静态 IP 且没有 DHCP 事务记录**时，EAPOL 认证会成功，但 IP 报文被静默丢弃 →
  现象是"认证成功却上不了网"。处置见 `diagnose.md`。

## 6. 服务器提示文本（`0x53` 属性）

`0x53` 不是错误码，而是**提示槽**：`<0x53><len><GBK 文本>`。同一字段在本接入点至少出现过：

| 文本（GBK） | 语感/含义 |
| --- | --- |
| `未使用锐捷客户端!` | 客户端形态被拒 |
| `锐捷客户端版本过低!` | 版本标识不符（对应 `0x11` 的版本字节） |
| `使用了非管理员指定的客户端!` | **客户端签名不符**（见 `signature.md`）；本笔记的目标之一就是消除这一句 |
| `您前一次上网没有正常下线!为保证您的账户正常,请再认证一次!` | 会话状态类 |
| `不在认证时段内` | 命中校方断网/禁认证时段（本接入点为工作日 01:00–05:00） |

另有两类文本出现在**成功**会话里（不在 `0x53`，属计费/服务段，例如"您当前使用的服务为…账户余额…计费策略…"与欢迎语），它们**不代表失败**。

解析提示文本必须按 TLV 逐条走并对 GBK 解码；早期实现把 `0x53` 段整段当"格式错误"丢弃，导致排障时看不到真实原因。

## 7. 编码与解析注意

- 帧尾有以太网最小长度填充（60 B），**必须按 EAP 长度字段截断**，否则填充的 `00 00` 会被误读成属性。
- 私有段起点 = 帧偏移 40（`eth 14 + eapol 4 + eap_hdr 4 + eap_type 1 + md5_value_size 1 + md5_value 16`）；终点 = `18 + EAP length`。
- 提示文本是 GBK；用 UTF-8 打印会看到乱码，别据此判定"格式错误"。
