# 客户端签名：`0x4d` / `0x60`（128 个十六进制字符）

> 这是什么：服务器（SAM）会校验"客户端是不是管理员指定的那个"。不符时回
> `0x53`「使用了非管理员指定的客户端!」。本文件给出该签名的**规格级**描述，
> 使他人可以自行实现；**不提供**从厂商二进制提取的表数据（见 `tables.md`）。
>
> 证据：本文件的事实来自对某一版本 Windows 客户端（V6.86 代次）的离线逆向，
> 以及同校区官方客户端的抓包对照。**尚未**由第三方独立复现，欢迎反馈（见 `verification.md`）。

## 1. 输出形态

- 属性 `0x4d` 与 `0x60` 内容相同，都是 **128 个十六进制字符**（即 64 字节数据的 hex 文本）。
- 参与计算的输入只有三样：**EAP-MD5 挑战**、**客户端自身 `.text` 镜像**、以及镜像上的一处变换（见 §2）。
  账号口令**不**参与签名运算（它参与的是另一条属性 `0x2f`）。

## 2. 输入的取得方式

| 输入 | 说明 |
| --- | --- |
| 挑战 `in16` | 服务器 EAP-Request/MD5 里的 16 字节值（**不是** EAP-Response 里的摘要） |
| 客户端镜像 `blob` | 客户端进程用 `VirtualQueryEx` 找到自己映像的第 2 个区域（= `.text`）并整段拷出；本版本长度 **2,809,856 字节** |
| 镜像上的变换 | 在哈希前，对 `blob[0x400:0x408]`（8 字节）做一次**确定性**块密码变换：明文 `0000005081ec8c00` → 密文 `853eac23ac4931ff`（与会话无关）。**该变换的算法尚未复刻**——实现时需要按同样方式从你自备的客户端里取这 8 字节 |

> 结论：**Windows 版没有 Linux 版那种静态指纹 blob**。"把 blob 抄进客户端"这条路对该版本不成立。

## 3. 变体分派

```c
/* in16[16] 为挑战（无符号字节） */
a  = (uint32_t)(int32_t)(int8_t)in16[1];
a += (uint32_t)(int32_t)(int8_t)in16[4];   /* 32 位回绕 */
var = a % 5u;                              /* 无符号取模 */
```

- 跳转表（本客户端版本）：`0 → 0x576630`、`1 → 0x576d40`、`2 → 0x577210`、`3 → 0x5769d0`、`4 → 0x571480`。
- **Python 陷阱**：`((b1-256 if b1>=128 else b1) + (b4-256 if b4>=128 else b4)) % 5` 与上式**不等价**（负数取模语义不同）。
  正确写法是先加 `2**32` 再取模：`a = (s8(b1) + s8(b4)) & 0xFFFFFFFF; var = a % 5`。
  本仓库 `reference/variant_dispatch.py` 实现了它，并用 `vectors/` 自测。
- 存在**第二条**取模链（`Vz_API`，下标 `0/3`、`(in16[0]+in16[3]) % 5`），与 `0/1/4` 那条的关系**未确认**；不要混用。

## 4. 四个被改写过的分组原语

客户端没有用标准算法，而是各自改了几处。以下按"与原版相比的差异"记录（常量属于该客户端版本）。

| # | 原语 | 状态宽度 | 关键差异（相对教科书实现） |
| --- | --- | --- | --- |
| P1 | **改版 SHA-1** | 20 B | 自定义 5×u32 IV；轮常量前三段为常数、第二段为"分组相关"，即轮 20–39 的常量 = `block[0] + 0x16AE9DEB`；**轮数切分 20/20/21/19**；收尾额外 `a += 1`；输出按**大端**取 5 个 u32 |
| P2 | **改版 MD5** | 16 B | 压缩 **共 128 轮**：前 64 轮更新 `a,b,c,d`，后 64 轮更新 4 个**影子槽**；每轮末尾 `+2`；有 6 轮把递增常量 `K`（初值 `0xbcdcb1f8`，轮间 `+= 1`）加进轮值；X 下标是按固定置换取；收尾为影子槽交叉相加，其中一项额外 `+1` |
| P3 | **改版 Tiger** | 24 B | 3 轮、每轮 8 个 round、乘数 **5/7/9**；**S 盒与标准 Tiger 完全相同**（可用公开实现，例如 minieap 的 `rjtiger_sbox.c`）；差异只有：自定义 IV、key schedule 的异或常量、**填充首字节 `0x01`**；收尾 `state[0]=a^aa; state[1]=b-bb; state[2]=c+cc` |
| P4 | **rjv3 版 Whirlpool** | 64 B | 10 轮；**状态 IV 次序 = `(0,3,5,2,1,7,4,6)`**；每轮末对状态字 **2/5/6 各 +1**；8×256 个 u64 表 + 11 条轮常量；**C0/C3/C7 三张表有 63 字节偏离教科书**（属厂商改动，必须从客户端提取）；收尾为 Miyaguchi–Preneel；padding 用 `0x80` + 补零 + 末尾**8 字节大端位长**；位长 ≥ 32 字节时**走两块**，第二块把位长以 **5 字节大端**写在 `[59:64]` |

## 5. 位切片变换（变体 1/2/4 的第二段必经步骤）

- 结构：`htonl` → 用固定种子建立 **128 字节轮密钥表** → 主循环每 8 字节：**位打包 → 16 轮混合（8 次查 `MIXT` 表）→ 位解包** → 再 `htonl`。
- 实测：**执行路径与输入无关**（46 组输入的地址轨迹与指令条数完全一致），因此可以逐条转写。
- 拆包/打包是**按位线性**的（只有 and/shl/shr/or），可以用"单比特探针"提取系数。
- 三处**必须从客户端提取**的数据：`MIXT`（8×64 的 u32 表）、打包系数、解包系数。
- 本步骤在不同变体里被调用的长度不同（16/16/64 字节）——见 §6。

## 6. 每个变体的拼装与输出切分

> 下表来自离线逆向报告。**"确认度"列如实标注**：`官方锚点` = 该变体有官方会话验证；
> `合成` = 只有合成向量/内部自洽；`未确认` = 细节仍需复核。实现时以 `vectors/` 里的期望值为准。

| 变体 | 拼装（在调用 P4 之前） | P4 输入长度 | 输出切分 | 确认度 |
| --- | --- | --- | --- | --- |
| 0 | `MD5hex(in16)` 前段 + `in16` 片段 + P1(20B) + `in16` 其余，并做 7 处字节微调 | 0x38 | 前 17 + 后 47（**不减下标**） | **官方锚点**（见 `vectors/official_anchors.json` 的 `official_retry v0`） |
| 1 | `hex(P2 的后 9 字节)` + 按符号分桶后的 `in16`；长度 = `50 + 6k`（k 为 `in16` 中 ≥0x80 的字节数） | 0x40 | `hex(P4 输出[::-1])` | 合成（无官方会话） |
| 2 | `P2[10:16] ‖ in16 ‖ P2[0:10] ‖ 原始 in16` | 0x30 | 后 32 减下标 + 前 32 | **官方锚点** |
| 3 | `P3(24B) ‖ in16[0:9] ‖ 00 ‖ P1(20B) ‖ in16[8:14]`（第 3 段 memcpy 长度是 20 而非 16） | 0x3c（走两块分支） | 前 16 减下标 + 后 48 | 合成（**无任何官方会话**） |
| 4 | `P3[0:16] ‖ in16[0:9] ‖ 0x48 ‖ P2[0:16] ‖ in16[10:16]`，随后**再就地过一遍位切片变换**（长度 0x40、另一套种子） | 0x30 → 0x40 | 前 32 + 后 32（逐字节 `+(i&1)`） | **官方锚点** |

已知的三处"容易读错"的细节（都来自报告）：`memcpy` 只取前 64 字节、某些字节**没有任何代码写**（靠 `memset` 留下的值）、以及同一函数被以不同长度重复调用。

## 7. 复用条件（什么时候这份规格失效）

只要出现下列任一变化，就必须重新分析并重算，**不要沿用本文的常量**：

1. 客户端版本升级（`.text` 长度或那 8 字节密文变化）；
2. 变体分派表或任一原语的 IV/轮常量变化；
3. 位切片变换的种子或表变化。

失效的典型症状：服务器回 `0x53`「使用了非管理员指定的客户端!」。

## 8. 本文件明确不提供的东西

- 任何"挑战 → 摘要"以外的厂商数据（表、镜像、二进制片段）；
- 口令派生属性 `0x2f` 的任何取值（那是账号敏感信息，本笔记一律不涉及）；
- 那处 8 字节块密码变换的算法（目前只知其确定性输入/输出，未复刻）。
